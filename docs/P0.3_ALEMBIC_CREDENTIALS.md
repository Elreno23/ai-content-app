# P0.3 — Migraciones Alembic y gestión de credenciales

> Documento técnico del bloque P0.3 del proyecto **ai-content**.
> Estado del bloque: **implementado y verificado** (con la BD real de desarrollo).

---

## 1. Problema original

Tres fallos verificados durante la auditoría:

1. **Cadena de migraciones destruida.** `backend/alembic/versions/` estaba vacío (solo
   archivos `.pyc` residuales); los `.py` de migración fueron borrados deliberadamente en
   los commits `fb094f5` ("drop legacy models and consolidate narrative schema") y
   anteriores. Consecuencia: el esquema de la BD no era reproducible; un entorno nuevo
   no podía reconstruirse con `alembic upgrade head`.
2. **Libro de estados desconectado.** La tabla `alembic_version` **existía pero estaba
   vacía** (sin `version_num`): alembic no sabía nada del estado real de la BD. La BD y
   el código habían quedado sin sincronizar.
3. **Credenciales commiteadas.** `backend/alembic.ini:89` contenía
   `sqlalchemy.url = postgresql+psycopg2://postgres:<contraseña>@localhost:5432/simulation_db`
   y **era la URL realmente usada** (`env.py:64-68` construía el motor desde la sección
   del `.ini`; no leía `.env`). Además `psycopg2-binary` estaba instalado en `venv311`
   pero ausente de `requirements.txt` (problema de reproducibilidad del entorno).

## 2. Estado real verificado antes del cambio (solo lectura)

```text
tablas public:            alembic_version, narrative
alembic_version:          vacía (sin revisión estampada)
columnas narrative:       id (int, secuencia nextval), episode_number (int NOT NULL),
                          create_at (timestamptz NOT NULL, default now()),
                          payload (jsonb NOT NULL)
índices:                  narrative_pkey (unique, id),
                          ix_narrative_episode_number (UNIQUE),
                          ix_narrative_id (btree)
```

El esquema coincidía **exactamente** con el modelo `app/models/narrative.py` — la BD
estaba sana; lo roto era la contabilidad de alembic y la configuración.

## 3. Cambios realizados

| Archivo | Cambio |
|---|---|
| `backend/alembic/env.py` | Carga `DATABASE_URL` desde `.env` (`load_dotenv`), lo valida (aborta con `RuntimeError` si falta) y deriva la URL síncrona reemplazando `+asyncpg` → `+psycopg2` para el motor de alembic |
| `backend/alembic.ini` | La línea con credenciales se sustituyó por un comentario que apunta a `env.py` como fuente de la URL |
| `backend/alembic/versions/0001_baseline_narrative.py` | **Nuevo**: migración baseline escrita a mano que replica el DDL verificado (`SERIAL`, unique index, `server_default now()`, JSONB); `downgrade()` inverso completo |
| `backend/requirements.txt` | Añadido `psycopg2-binary==2.9.12` (ya instalado en el venv; solo se fija) |

## 4. Contrato operativo de migraciones

Flujo instalado: **modelo (`app/models`) → baseline (`alembic/versions/`) → estado
(`alembic_version`)**, con la configuración en un único lugar (`backend/.env`).

Comandos válidos a partir de ahora:

| Comando | Cuándo usarlo |
|---|---|
| `alembic upgrade head` | Entorno nuevo: crea el esquema desde cero |
| `alembic revision --autogenerate -m "..."` | Cada cambio futuro de modelos (comparar el SQL generado antes de aplicar) |
| `alembic upgrade head` | Aplicar migraciones nuevas al entorno actual |
| `alembic current` / `alembic history` | Diagnóstico del libro de estados |

Decisiones técnicas:

1. **Baseline único en vez de restaurar la cadena borrada**: las migraciones eliminadas
   describían esquemas legacy ya eliminados; reconstruirlas añadiría ruido sin valor.
2. **`alembic stamp head` en vez de `upgrade`**: la tabla `narrative` ya existía y
   coincidía con el baseline; `upgrade` habría intentado `CREATE TABLE` y fallado. El
   `stamp` sincroniza el libro de estados **sin ejecutar DDL** (escribe 1 fila en
   `alembic_version`). Reversible con `alembic stamp base`.
3. **Motor síncrono para alembic** (`psycopg2`) mientras la app usa async (`asyncpg`):
   patrón estándar; alembic no participa en el runtime de la app y el `replace()`
   mantiene una única fuente de configuración.

## 6. Limitaciones y riesgos pendientes

1. **⚠️ Rotación de credencial (acción del usuario, fuera del bloque).** La contraseña
   se eliminó de `alembic.ini`, pero **permanece en el historial de git** (commits
   anteriores). Extraer el archivo actual no borra el historial: hay que cambiar la
   contraseña del usuario `postgres` (y, si el repo se comparte, considerar
   `git filter-repo` o aceptar la exposición).
2. **Sin índice GIN sobre `payload`** (JSONB): decisión de diseño diferida al bloque de
   trazabilidad; si se consultan acciones dentro del JSONB, se añadirá entonces.
3. **`narrative_pkey` se crea como índice unique por PostgreSQL** al definir la PK — el
   baseline lo reproduce implícitamente vía `PrimaryKeyConstraint`; comportamiento
   estándar, sin acción pendiente.
4. **El `echo=True` del engine de la app** sigue activo (ruido de logs SQL) — pendiente
   del bloque P1 de configuración.
5. **Sin base de datos de prueba**: las migraciones futuras se validarán primero en este
   entorno; conviene crear una BD de test cuando se implemente la suite pytest.
